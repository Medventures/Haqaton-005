# Clinic Assistant — слайды и сценарий демо

## Слайды

### 1. Проблема

Пациенту бывает трудно понять, к какому специалисту обратиться, сколько стоит приём и когда есть свободный слот. Администратор отвечает на одни и те же вопросы, а сообщение с тревожными симптомами может потеряться в общем потоке.

### 2. Решение

Clinic Assistant общается на русском и казахском, уточняет жалобу, подбирает специальность, показывает цены и свободные слоты из каталога. Пациент может сразу попросить оператора. Бот не ставит диагноз и не назначает лечение.

### 3. Архитектура

```text
Пациент → Go API → red-правила (до LLM) → 103/112 + оператор
               ├→ LLM через Ollama → JSON-извлечение и текст ответа
               ├→ каталог JSON → услуги, цены и слоты
               └↔ PostgreSQL → диалоги и обращения оператору
```

Red-фразы проверяются кодом до LLM на каждом сообщении. Для остальных запросов LLM возвращает структурированный JSON; сервер проверяет specialty id и сам выбирает услуги и слоты из каталога. Диалоги и обращения к оператору хранятся в PostgreSQL.

### 4. Безопасность

- Локальная Ollama и PostgreSQL работают внутри контура развертывания; запросы не отправляются в OpenAI или сторонние LLM сервисы. Для production весь стек размещается в защищённом контуре клиники.
- Доступ к истории диалогов разграничен: пациент видит только свои диалоги, оператор — очередь обращений.
- Red-маршрут детерминированный и не вызывает LLM; пациенту показываются номера 103 (скорая помощь) и 112 (единая служба экстренной помощи), диалог передаётся оператору.
- Бот не диагностирует, не назначает лекарства и использует только цены, услуги и слоты из каталога.
- Желтый уровень подсказывает обратиться за медицинской помощью; это не медицинская оценка.
- Набор фраз может пропускать симптомы или срабатывать ошибочно. При непосредственной опасности нужно обращаться в экстренную службу.

### 5. Следующие шаги

- Дообучить локальную модель на обезличенных диалогах контакт-центра и дополнить базу знаний клиники. Сейчас используется готовая instruct-модель; данных для такого дообучения в репозитории нет.
- Интегрировать каталог, расписание и запись с МИС клиники.
- Дополнить OpenAPI контрактом реальной интеграции и проверками совместимости.
- Проверить русские и казахские формулировки с врачом и измерить ошибки на репрезентативных обращениях.
- Усилить разграничение доступа операторов и добавить аудит доступа к диалогам.

## Сценарий демо на 3–5 минут

Перед показом выполнить `docker compose up -d --build`, загрузить модель командой из README и убедиться, что Ollama запущена. Получить анонимный токен пациента по инструкции в README.

1. **Green — подбор (около минуты).** Написать: «Третий день болит горло и заложен нос». Показать, что бот определяет ЛОРа и выводит услуги, цену и свободный слот из каталога. Обратить внимание: диагноз не предлагается.
2. **Yellow — обратиться в ближайшее время (около минуты).** В новом диалоге написать: «У ребёнка второй день температура и кашель». Показать жёлтый уровень и рекомендацию связаться с клиникой или обратиться за медицинской помощью.
3. **Red — экстренный маршрут (около минуты).** Написать: «Давит в груди, трудно дышать». Показать немедленный ответ с номерами 103 и 112 и передачу оператору; этот маршрут срабатывает до вызова LLM.
4. **Оператор (около минуты).** В новом диалоге написать: «Позовите оператора». Показать статус передачи и очередь оператора. Войти демо-учётной записью `operator1 / operator1` и открыть очередь.

Для воспроизводимых проверок вместо живой демонстрации запустить `./data/run_tests.sh` при поднятом API. Ответы LLM могут различаться, поэтому таблица теста показывает фактические совпадения для текущего запуска.
